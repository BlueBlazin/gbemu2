Let's recap where we are at. We have:
- A cycle accurate emulator
- Using a custom driver and async-await
- A pixel FIFO based cycle accurate PPU implementation (src/ppu.rs)
- Missing APU and Joypad (that's fine we'll implement them later)

Now we need to implement the actual UI for the emulator. Let's defer worrying about audio for when we implement the APU and keyboard input for when we add Joypad support. For now let's focus on displaying to the screen.

Review of what we have and how we want it to work:

Our `Driver` (src/driver.rs) has the following method:

```rs
pub enum Event {
    VBlank,          // Frame complete, display framebuffer to screen
    AudioBufferFull, // Audio buffer full, drain to audio system
    MaxCycles,       // Reached cycle limit
}

pub struct ExecutionResult {
    pub event: Event,
    pub cycles_executed: usize,
}

pub fn run_for(&mut self, max_cycles: usize) -> ExecutionResult
```

The main idea is that we want to run the emulator for the full MAX_CYCLES every 1/60 seconds.
Since the gameboy runs at 4.194304 MHz frequency, we correctly have `MAX_CYCLES = 69905`.

In something like Javascript, we'd simply do this by using something like a `setTimeout` or `requestAnimationFrame`.

The second main idea is that we want the components of the emulator to be able to trigger various events (NOT interrupts which may overlap with events but are separate).
These events are basically used by the UI library (not the gameboy emulator code) to do stuff with the outside world.

The most important perhaps is VBlank where we want to update/redraw the screen.
Also, if an event happens, the `run_for` method is cut short. So it also returns the number of cycles executed.
So we need to then rerun it for the remainder of the cycles. Once again, the goal is to run the emulator for MAX_CYCLES number of cycles in our 1/60 seconds interval for 60 FPS.

We also have code to init the emulator in src/emulator.rs.
